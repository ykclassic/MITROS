# Phase 12 — Execution Gateways

MITROS now has a single application-level execution boundary between approved trade proposals and venue adapters.

## Flow

Strategy / Intelligence -> Risk Engine -> Trade Proposal -> Human Approval -> ProposalExecutionGateway -> Venue Gateway.

## Execution contract

`ExecutionGateway` defines the only `submit()` and `reconcile()` operations exposed to venue execution. Orders are immutable value objects with explicit venue, asset, side, quantity and order type.

## Approval capability

`ProposalExecutionGateway` requires:
- `TradeProposal.approval_status == APPROVED`;
- an approval-token digest configured outside the proposal;
- a token whose SHA-256 digest matches the configured digest.

Invalid, missing, or forged tokens fail closed. The gateway never creates or changes approval decisions.

## Venue adapters

- `PaperExecutionGateway` provides deterministic idempotent execution for tests/demo validation.
- `MT5ExecutionGateway` is an isolated adapter boundary. The core package does not import the MT5 SDK; a deployment-specific client is injected into the adapter.

## Idempotency and reconciliation

Client order ID is the immutable proposal ID. The paper gateway returns the existing result for repeated submissions and supports reconciliation by client order ID. Real venue adapters must preserve the same contract.

## Security boundary

- Strategy, intelligence, research and risk packages have no execution capability.
- Human approval remains mandatory.
- Approval tokens are never generated by the execution gateway.
- Venue credentials/client objects are injected only into the isolated gateway.
- No credentials are stored in source code.
- Phase 12 introduces the execution boundary but does not configure a live broker account or submit a live MT5 order.

## Next phase

Durable execution ledger and reconciliation should persist submission intent, gateway responses, uncertain outcomes and venue reconciliation before live trading is enabled.
